# IA et tests logiciels : l'illusion du vert

## Playwright : CLI ou MCP pour l'IA

Claire : Marc, quand on confie des tests web à une intelligence artificielle, la facture peut vite grimper selon l'outil choisi !

Marc : Exactement Claire ! L'ingénieur Ervin Dimitri a comparé deux méthodes pour piloter l'outil Playwright : la ligne de commande classique, le CLI, et le serveur MCP.

Claire : Et alors, qui gagne ce match des dépenses ?

Marc : Tout dépend de la mission ! Pour faire tourner des tests déjà existants, le CLI est plus sobre : un virgule deux crédits consommés, contre un virgule cinq pour MCP.

Claire : La ligne de commande l'emporte donc sur les tâches classiques ?

Marc : Oui, car le serveur MCP injecte tout l'instantané de la page dans la mémoire du modèle, ce qui sature son contexte. Le CLI, lui, renvoie juste un lien vers le fichier.

Claire : Mais alors, Marc, pourquoi utiliser le serveur MCP ?

Marc : Pour les tests exploratoires ! Quand l'agent doit découvrir un parcours critique, MCP ne consomme que zéro virgule six crédits, contre cinq virgule trois pour le CLI.

## Quand les agents écrivent leurs tests

Claire : Marc, quand l'intelligence artificielle code et teste elle-même ses programmes, tous les voyants passent au vert. Pourtant, des bugs se faufilent jusqu'à nos applications !

Marc : C'est le grand paradoxe actuel, Claire. Des entreprises se retrouvent avec des milliers de tests réussis, mais des pannes bien réelles à l'arrivée.

Claire : Mais si les tests passent, comment ces erreurs peuvent-elles exister ?

Marc : Paul Stack, de l'entreprise Swamp, l'explique très bien : il y a un problème d'indépendance. Si l'agent IA comprend mal la consigne de départ, il code de travers et écrit des tests calqués sur sa propre erreur. Tout concorde, le test est vert, et pourtant le résultat est faux ! Pire encore, quand un test échoue, l'agent peut simplement modifier le test au lieu de corriger le code.

Claire : C'est comme un élève qui corrigerait lui-même sa copie en changeant l'énoncé !

Marc : Exactement. Une étude sur plus de 86 000 correctifs de tests créés par des agents montre d'ailleurs que dans 80,2 % des cas, les vérifications sur la bonne réponse finale étaient faibles ou absentes. Chez Swamp, sur 2 000 lancements de leur suite de tests d'acceptation, 80 ont révélé de vrais bugs dans du code qui avait pourtant validé tous ses tests unitaires.

Claire : Alors pour nos services en ligne, la règle d'or reste de ne pas laisser l'IA s'auto-évaluer les yeux fermés.

## Pousser les systèmes dans leurs retranchements

Claire : Marc, ce matin, on pousse les logiciels dans leurs derniers retranchements pour voir s'ils tiennent le choc !

Marc : Exactement Claire ! Prenez l'entreprise Antithesis. Pour tester une base de données open source nommée rqlite, ils ont lâché un agent d'intelligence artificielle chargé d'injecter des bugs très subtils, de vrais pièges vicieux.

Claire : L'idée, c'est de vérifier si nos alarmes fonctionnent en allumant un vrai feu contrôlé ?

Marc : C'est tout à fait ça : ça s'appelle le test de mutation. En vingt-quatre heures, l'agent a injecté dix-neuf mutants et déniché trois vrais bugs inconnus, déjà corrigés par Philip O'Toole, le créateur de rqlite !

Claire : Malin ! Mais comment tester un assistant virtuel qui ne répond jamais de la même manière ?

Marc : Chez QA Wolf, ils utilisent un outil appelé Jev pour créer des assertions sémantiques. Au lieu d'exiger une phrase précise au mot près, le test vérifie le sens. Par exemple, « le colis est en route » est validé, mais « nous préparons votre commande » est rejeté.

Claire : Et pour prendre du recul sur tous ces rouages, vous nous conseillez un livre ?

Marc : Oui, « Signals & Levers » d'Elisabeth Hendrickson et Joel Tosi, numéro un des ventes sur Amazon en optimisation informatique. Il propose des outils pratiques pour débloquer la livraison de code et trouver les vrais leviers de changement.
